JWT는 비대칭 서명만 쓰는 형식이 아닙니다. **HMAC 같은 대칭키 방식(`HS256`)도 표준에 포함**되어 있고, 어떤 방식으로 검증할지는 **토큰 헤더의 `alg`** 가 알려줍니다. 검증하는 쪽이 이 값을 그대로 믿으면, 공격자가 `alg`를 `HS256`으로 바꾸고 **누구나 받을 수 있는 공개키를 HMAC 키로 써서** 만든 토큰이 통과합니다. 이를 **alg confusion**이라고 하며, 막으려면 허용할 알고리즘을 토큰이 아니라 **서버가 정해야** 합니다.

**JWT는 비대칭 서명인가요**

JWT는 `헤더.페이로드.서명` 모양을 정한 형식일 뿐이고, 서명 부분을 무엇으로 만들지는 헤더의 `alg`가 정합니다. JWS 스펙(RFC 7515)은 처음부터 내용을 "digital signature **or MAC**"으로 보호한다고 적고 있습니다.

RFC 7518이 정한 대표 알고리즘의 구현 요구 수준은 다음과 같습니다.

| `alg` | 방식 | 구현 요구 |
|---|---|---|
| `HS256` | HMAC-SHA256 (대칭) | **Required** |
| `RS256` | RSA PKCS#1 v1.5 + SHA-256 (비대칭) | Recommended |
| `ES256` | ECDSA P-256 + SHA-256 (비대칭) | Recommended+ |
| `none` | 서명 없음 | Optional |

반드시 구현해야 하는 쪽이 오히려 대칭키 방식입니다. 그래서 대부분의 JWT 라이브러리는 하나의 검증 함수로 HS256과 RS256을 모두 처리합니다.

**HMAC은 무엇이고, 언제 쓰나요**

HMAC은 **비밀키를 섞어서 계산하는 해시**입니다. 보내는 쪽은 `HMAC(키, 메시지)`로 태그를 만들어 메시지와 함께 보내고, 받는 쪽은 자신이 가진 같은 키로 다시 계산해 비교합니다. 키는 망으로 보내지 않고 양쪽이 미리 나눠 갖습니다.

HMAC은 빠르지만, **검증할 수 있는 쪽은 곧 만들 수도 있는 쪽**입니다. 이 차이가 언제 무엇을 쓸지를 가릅니다.

| | HS256 | RS256 / ES256 |
|---|---|---|
| 서명 키 | 공유 비밀키 | 개인키 (발급자만 보유) |
| 검증 키 | 같은 공유 비밀키 | 공개키 (누구나 받아도 됨) |
| 검증하는 쪽이 토큰을 만들 수 있나 | 있음 | 없음 |
| 어울리는 곳 | 발급자와 검증자가 같은 서비스 | 발급자와 검증자가 다른 경우 (IdP) |

서비스 열 곳이 HS256 키를 나눠 가지면, 그중 한 곳만 털려도 **모든 서비스에서 통하는 토큰**을 만들 수 있습니다. 그래서 여러 서비스가 토큰을 검증하는 IdP는 개인키를 발급자만 갖는 비대칭 방식을 씁니다.

**헤더 한 줄로 위조 토큰이 통과하는 과정**

서버는 RS256으로 서명하고, 검증 코드는 아래처럼 키 하나만 넘긴다고 가정합니다.

```text
verify(token, publicKey)   // 알고리즘은 token 헤더의 alg를 보고 결정
```

공격자는 다음 순서로 토큰을 만듭니다.

1. JWKS 엔드포인트 등에서 서버의 **공개키**를 받습니다. 원래 공개된 값입니다.
2. 페이로드를 `"sub": "admin"`처럼 원하는 대로 바꿉니다.
3. 헤더의 `alg`를 `RS256`에서 `HS256`으로 바꿉니다.
4. `HMAC-SHA256(헤더.페이로드, 키 = 공개키 바이트)`로 서명 부분을 만듭니다.

검증 쪽에서는 이렇게 처리됩니다.

```text
헤더 alg = HS256  → HMAC으로 검증하기로 결정
HMAC 키 자리     → 넘겨받은 publicKey를 그대로 사용
HMAC(publicKey, 헤더.페이로드) == 토큰의 서명  → 통과
```

공격자와 서버가 같은 공개키로 HMAC을 계산했으니 결과가 일치합니다. 문제는 **서버가 자기 공개키를 HMAC 비밀키 자리에 넣은 것**입니다. "공개키는 공개돼도 안전하다"는 전제는 그 키를 RSA나 ECDSA 검증에 쓸 때만 성립합니다. HMAC 키로 쓰이는 순간 공개된 비밀키가 됩니다.

이 공격은 2015년 Node.js `jsonwebtoken`을 비롯한 여러 언어의 라이브러리에서 실제로 발견됐습니다. 키를 PEM 문자열이나 바이트로 받는 API가 특히 취약했습니다. RSA 공개키든 HMAC 비밀키든 같은 타입으로 들어오니 구분할 수 없었기 때문입니다.

**같은 뿌리의 다른 공격**

공통된 원인은 **검증 방법을 검증 대상(토큰)이 정하게 둔 것**입니다.

- **`alg: none`**: 서명 없는 토큰입니다. 라이브러리가 `none`을 허용하면 서명 부분을 비워도 통과합니다.
- **`jku`** (RFC 7515 4.1.2절): 검증 키를 내려받을 URL을 헤더에 적을 수 있습니다. 이 값을 따라가면 공격자가 자기 서버에 올린 공개키로 검증하게 됩니다.
- **`kid`**: 여러 키 중 무엇을 쓸지 고르는 값입니다. 이 값을 파일 경로나 DB 쿼리에 그대로 넣으면 경로 조작이나 SQL 인젝션으로 이어집니다.
