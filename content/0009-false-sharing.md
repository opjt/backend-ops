서로 다른 코어가 서로 다른 변수를 수정하더라도, 두 변수가 같은 캐시라인에 있으면 **그 캐시라인이 코어 사이를 왕복하는 비용 때문에 느려지는 현상**이 생겨요. 이를 **False sharing**이라고 해요. 실제로 공유하는 데이터는 없는데 CPU가 캐시라인 단위로 공유하는 것처럼 다루기 때문에 "false"라고 불러요. 변수 사이에 **패딩을 넣어 서로 다른 캐시라인에 떨어뜨리면** 해결돼요.

**캐시는 변수가 아니라 캐시라인 단위로 움직여요**

CPU는 메모리에서 8바이트짜리 `int64` 하나만 필요해도 그 주변을 포함한 덩어리 하나를 통째로 캐시로 가져와요. 이 덩어리가 **캐시라인**이고, x86에서는 64바이트, Apple M1에서는 128바이트로 보고돼요. 메모리 접근은 캐시보다 수십~수백 배 느리고, 프로그램은 방금 쓴 주소 근처를 곧 또 쓰는 경향(공간 지역성)이 있어서 한 번 갈 때 많이 가져오는 게 이득이에요.

문제는 **L1 캐시가 코어마다 따로 있다**는 점이에요. 여러 코어가 같은 캐시라인을 **읽기만** 할 때는 각자 복사본을 들고 있어도 괜찮아요. 하지만 한 캐시라인에 **쓸 수 있는 코어는 한 번에 하나뿐**이에요. 그래서 쓰기는 이렇게 진행돼요.

1. 코어 A가 쓰려면 그 캐시라인의 소유권을 가져오고, 다른 코어에 있던 복사본은 **무효화**돼요.
2. 코어 B가 같은 캐시라인의 다른 변수에 쓰려면, 다시 소유권을 가져오고 A의 복사본을 무효화해요.
3. 두 코어가 번갈아 쓰면 캐시라인이 코어 사이를 계속 왕복하고, 쓰기는 소유권이 넘어올 때마다 기다려요.

느려지는 이유는 락이 아니라 **캐시라인을 주고받는 비용**이에요. 결과는 정확하게 나오지만 시간이 오래 걸려요.

**측정: 패딩 유무**

고루틴 두 개가 같은 구조체의 `A`, `B` 필드를 각자 `b.N`번씩 증가시키는 벤치마크예요.

```go
type noPad struct {
	A int64
	B int64
}

type pad120 struct {
	A       int64
	padding [120]byte // A 시작부터 B 시작까지 128바이트
	B       int64
}

func bench(b *testing.B, a, c *int64) {
	var wg sync.WaitGroup
	wg.Add(2)
	go func() {
		defer wg.Done()
		for i := 0; i < b.N; i++ {
			atomic.AddInt64(a, 1)
		}
	}()
	go func() {
		defer wg.Done()
		for i := 0; i < b.N; i++ {
			atomic.AddInt64(c, 1)
		}
	}()
	wg.Wait()
}
```

두 고루틴은 서로 다른 필드만 쓰니까 데이터 레이스는 없어요. 그래도 `atomic`을 쓴 건, 여러 코어가 같이 쓰는 카운터는 실제로 보통 `atomic`이기 때문이에요. 그냥 `++`로 바꿔도 false sharing은 보이지만 차이가 줄어들어요(M1, 약 2.6배).

패딩 없음과 120바이트 패딩을 `go test -bench . -count 5`로 잰 평균이에요.

| 환경 | 패딩 없음 | 120바이트 | 차이 |
|---|---|---|---|
| Apple M1 Pro | 51.3 ns | 9.07 ns | 약 5.7배 |
| x86 VM (QEMU, 6 vCPU) | 20.8 ns | 1.66 ns | 약 12.5배 |

필드 하나를 추가했을 뿐인데 두 환경 모두 크게 빨라졌어요.

**해결 방법**

- **패딩**: 자주 쓰이는 필드 사이를 캐시라인 크기만큼 떨어뜨려요. Go 표준 라이브러리도 이렇게 해요. `sync.Pool`의 P별 저장소에는 다음 패딩이 들어 있어요.

  ```go
  // Prevents false sharing on widespread platforms with
  // 128 mod (cache line size) = 0 .
  pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte
  ```

  64바이트와 128바이트 캐시라인 모두에서 안전하도록 128을 썼어요. Go 런타임 내부의 `internal/cpu.CacheLinePadSize`도 arm64는 128, x86은 64로 정해져 있어요.
- **쓰기를 나누기**: 카운터 하나를 여러 코어가 두드리는 대신, 코어(Go에서는 P)마다 따로 두고 읽을 때 합쳐요. `sync.Pool`이 P별 저장소를 두는 것도 같은 이유예요.

패딩은 메모리를 더 쓰는 대가예요. 그래서 모든 구조체에 넣는 게 아니라, **여러 코어가 동시에 자주 쓰는 필드**에만 넣어요. 읽기만 하는 필드끼리는 같은 캐시라인에 있어도 괜찮지만, 자주 쓰이는 필드 옆에 있으면 그 필드가 쓰일 때마다 함께 무효화되니 떨어뜨리는 게 좋아요.

- 마이크로벤치마크라서 실제 서비스의 손해는 접근 빈도에 따라 훨씬 작을 수 있어요. 의심될 때는 패딩 전후를 직접 재보는 게 가장 확실해요.
